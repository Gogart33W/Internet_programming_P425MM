## 1. Архітектура адаптивності (Mobile-First)

У роботі впроваджено концепцію **Mobile-First**: базові CSS-правила описують компактний інтерфейс для мобільного пристрою (320–360px), а медіа-запити (`@media (min-width: ...)`) поступово розширюють композицію для планшетів та десктопів.

### Обрані Breakpoints та їх обґрунтування (Content-Driven)
1. **`min-width: 48rem` (768px) — Tablet / Medium Viewport**:
   - *Причина введення:* при цій ширині з'являється достатній горизонтальний простір, щоб розмістити ігрове поле Tetris та бічну панель зі статистикою пліч-о-пліч, а навігаційні посилання шапки перевести з вертикального/обгорнутого списку в горизонтальний ряд `space-between`.
2. **`min-width: 64rem` (1024px) — Desktop / Large Viewport**:
   - *Причина введення:* перехід до просторого десктопного макета зі збільшеними відступами (`gap: var(--space-12)`), розширеною формою налаштування режимів та фіксацією максимальної ширини контейнера `width: min(100% - 2rem, 72rem)`.

## 2. Застосування Flexbox та CSS Grid

### Де використано Flexbox (одновимірні компоненти):
- **Шапка сайту (`.app-header .header-inner`)**: на мобільних пристроях елементи розташовані у колонку по центру, на планшетах і вище перемикаються на `display: flex; flex-direction: row; justify-content: space-between;`.
- **Список навігації (`.nav-list`)**: `display: flex; flex-wrap: wrap; gap: var(--space-2);` з великими touch-target посиланнями (min 44px).
- **Група кнопок форми (`.form-actions`)**: реалізовано правило `display: flex; flex-wrap: wrap; gap: 0.75rem;`, де дочірні кнопки мають `flex: 1 1 10rem;`. На вузькому екрані кнопки автоматично займають по 100% ширини і розташовуються одна під одною, а на ширшому — встають в один ряд.
- **Внутрішня структура ігрової картки (`.game-board-card`)** та списку клавіш керування.

### Де використано CSS Grid (двовимірні області та авто-сітки):
- **Головна композиція гри (`.game-layout`)**: 
  - На mobile: `display: grid; grid-template-columns: 1fr;` (одна колонка, центрована).
  - На tablet/desktop: `grid-template-columns: 260px 240px;` (або флюїдні межі з `gap: var(--space-8)`).
- **Мобільна сітка карток статистики (`.game-sidebar`)**: на вузьких екранах блоки рахунку, наступної фігури та керування шикуються в компактну двоколонкову сітку через `repeat(auto-fit, minmax(min(100%, 140px), 1fr))`.
- **Групи вибору бонусів (`.choice-list`)**: адаптивна сітка `grid-template-columns: repeat(auto-fit, minmax(min(100%, 14rem), 1fr)); gap: var(--space-3);`, що забезпечує охайний розподіл чекбоксів без порожнеч.

## 3. Три діагностовані responsive-проблеми та способи їх усунення

### Проблема 1. Горизонтальне переповнення (Horizontal Overflow) на ширині 320–360px
- **Симптом:** На найвужчих екранах з'являлася горизонтальна смуга прокручування через фіксовану ширину SVG-зображення ігрового поля (240px) разом із внутрішніми та зовнішніми відступами картки.
- **Діагностика:** Перевірка `clientWidth` елементів у Responsive Mode показала вихід картки за межі екрана.
- **Виправлення:** Для зображень задано `max-inline-size: 100%; block-size: auto; aspect-ratio: 240 / 400;`, а для контейнера ігрового поля — `width: 100%; max-inline-size: 300px;`. Горизонтальний скрол повністю зник без застосування шкідливого `overflow-x: hidden`.

### Проблема 2. Злипання та недостатній розмір сенсорних зон (Touch Targets)
- **Симптом:** Посилання в меню та чекбокси на екранах смартфонів мали занадто малу площу натискання, через що користувач міг випадково натиснути сусідній пункт.
- **Діагностика:** Аудит DevTools Accessibility показав невідповідність стандарту Google Lighthouse (мінімум 44×44px для інтерактивних елементів).
- **Виправлення:** Для `.nav-link` та `.button` задано `min-height: 44px`, а для рядків чекбоксів `.choice-label` — `min-height: 36px` та збільшено проміжки `gap: var(--space-3)`.

### Проблема 3. Ламання кнопок форми на вузькому екрані (Скасувати / Зберегти)
- **Симптом:** При ширині 360px кнопки в рядку сабміту вилазили за праву межу картки або стискалися до нечитабельного стану.
- **Діагностика:** Використання фіксованих ширин без адаптивності.
- **Виправлення:** Впроваджено гнучкий flex-контейнер `.form-actions` із властивістю `flex-wrap: wrap` та базовим базисом `flex: 1 1 10rem`, завдяки чому кнопки акуратно шикуються в колонку на смартфоні та стають у ряд на десктопі.

## 5. Відповіді на контрольні питання

### 1. Що означає mobile-first у вашому CSS?
Mobile-first означає, що базові стилі (поза медіа-запитами) створюються для найпростішого, компактного та вузького мобільного екрана. Більш складні багатоколонкові макети, специфічні розміщення та додаткові ефекти нашаровуються виключно через медіа-запити з умовою `@media (min-width: ...)`.

### 2. За якою ознакою вибрано breakpoints?
Точки зупинки (breakpoints) обрано за принципом **content-driven** (відповідно до потреб вмісту), а не прив'язуючись до розмірів конкретних моделей смартфонів (наприклад, iPhone чи iPad). Точку 48rem (768px) було призначено в момент, коли ширини вікна стає достатньо для розміщення ігрового поля та панелі поруч, а 64rem (1024px) — коли з'являється простір для повноцінної десктопної сітки.

### 3. Які частини краще розв'язав Flexbox?
Flexbox ідеально підійшов для одновимірних (1D) компонентів: вирівнювання елементів шапки в рядок або стовпчик, адаптивного ряду навігаційних посилань, гнучкого групування кнопок дій форми (`.form-actions`) з переносом рядків (`flex-wrap`).

### 4. Які частини краще розв'язав Grid?
CSS Grid ефективно розв'язав завдання двовимірного (2D) розташування: побудову головної композиції сторінки гри (`.game-layout`), де потрібно чітко керувати колонками ігрового поля та панелі статистики, а також авто-сітку чекбоксів та радіокнопок у формі налаштування режиму.

### 5. Як працює `repeat(auto-fit, minmax(...))`?
Функція `repeat(auto-fit, minmax(min_width, 1fr))` автоматично розраховує, скільки колонок заданої мінімальної ширини може поміститися у контейнері. Якщо місця недостатньо, елементи автоматично переносяться на новий рядок, а наявний простір рівномірно розподіляється (`1fr`), що усуває потребу створювати окремі breakpoints для кожної кількості колонок.

### 6. Чому `order` може погіршити доступність?
Властивість `order` змінює виключно візуальне розташування елемента на екрані, не змінюючи реального порядку вузлів у DOM-дереві. Програми екранного доступу (скрінрідери) та навігація за допомогою клавіші `Tab` слідують порядку в HTML, тому візуальна невідповідність дезорієнтує незрячих людей та користувачів клавіатури.

### 7. Як перевірити причину horizontal overflow?
За допомогою DevTools: запустити скрипт у консолі, який знаходить елементи з `scrollWidth > clientWidth`, або ввімкнути режим адаптивного дизайну (Responsive Mode) і проінспектувати DOM-дерево, шукаючи підсвічені елементи, що виходять за синій контур viewport.

### 8. Чому `overflow-x: hidden` не є універсальним виправленням?
Встановлення `overflow-x: hidden` на `body` лише візуально обрізає контент, який виліз за межі екрана, маскуючи баг. При цьому користувач втрачає доступ до обрізаного тексту чи кнопок, а в деяких браузерах це блокує нормальне функціонування `position: sticky`.

### 9. Як zoom 200% вплинув на макет?
При збільшенні масштабу сторінки до 200% ширина доступного viewport у пікселях CSS зменшується вдвічі. Завдяки mobile-first та fluid-верстці макет автоматично перебудувався у свою компактну мобільну версію (1 колонка), без втрати вмісту і без горизонтального переповнення.

### 10. Які зміни виконує `prefers-reduced-motion`?
Медіа-запит `@media (prefers-reduced-motion: reduce)` зчитує системне налаштування операційної системи користувача і зменшує або повністю вимикає тривалість переходів (`transition-duration: 0.01ms`) та анімацій, запобігаючи запамороченню та нудоті в людей із вестибулярними порушеннями.
