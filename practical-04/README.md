## 1. Архітектура та організація CSS

Для проєкту організовано єдиний модульний файл `styles/main.css` відповідно до принципу зростання специфічності:
1. **Tokens та базові змінні (`:root`)**: оголошено кольорову палітру темного неонового стилю Tetris, системні відступи (`--space-*`), радіуси заокруглень (`--radius-*`), типографіку та тіні (`--shadow-*`).
2. **Reset & Base Rules**: коректне налаштування `box-sizing: border-box`, безпечне обнулення `margin: 0` для `body`, гнучкі зображення (`max-inline-size: 100%`, `block-size: auto`) та забезпечення доступного `skip-link`.
3. **Layout primitives**: центральний гнучкий контейнер `.container`, адаптивна секція `.game-layout`.
4. **Типографіка**: заголовки з адаптивним розміром через `clamp()`, посилання з підкресленням та чіткими станами взаємодії.
5. **Компоненти**: незалежні блоки `.card`, `.button` (з модифікаторами `--secondary`, `--danger`, `--full`), `.field-control` та декоративні картки статистики гри.
6. **Accessibility & States**: підтримка `:hover`, `:focus-visible`, `:active`, `:disabled`, `:invalid:not(:placeholder-shown)` та медіа-запиту `prefers-reduced-motion`.

## 2. Діагностика каскаду та виправлені проблеми у DevTools

У процесі налаштування стилів та тестування засобами Browser DevTools було виявлено, проаналізовано та вирішено два конфлікти специфічності й спадкування:

### Проблема 1. Перекриття фону та кольору тексту для вторинної кнопки (`.button--secondary`)
- **Симптом:** При додаванні модифікатора класу `.button--secondary` кнопка скасування або вибору режиму не набувала прозорого фону та бірюзової межі, а зберігала суцільний фіолетовий фон базової кнопки.
- **Діагностика у DevTools (Computed/Styles):** Правило `.button { background-color: var(--color-primary); }` мало однаковий рівень специфічності `(0, 1, 0)` з класом `.button--secondary`. Проте через порядок оголошення в коді або конфлікт селекторів стилі базової кнопки перезаписували модифікатор.
- **Виправлення:** Впорядковано правила за принципом BEM/SMACSS: базовий клас `.button` оголошено перед модифікаторами. Для модифікатора `.button--secondary` чітко перевизначено властивості `background-color: transparent; border-color: var(--color-accent); color: var(--color-accent);` без використання `!important`.

### Проблема 2. Зникнення контрастного фокусу (Focus Ring) у полів введення форми
- **Симптом:** При фокусуванні за допомогою клавіатури (`Tab`) поле введення втрачало системну рамку фокусу, через що користувачеві було важко зрозуміти активний елемент.
- **Діагностика у DevTools:** Застосування класичного скидання `outline: none` у загальному правилі прибирало фокус, не залишаючи доступної альтернативи.
- **Виправлення:** Впроваджено сучасний псевдоклас `:focus-visible` із подвійним акцентом: чіткий контур `outline: 2px solid var(--color-accent); outline-offset: 1px;` разом із фірмовим неоновим підсвічуванням `box-shadow: var(--shadow-focus);`. Це гарантує високу вебдоступність (WCAG 2.1) для людей, які користуються клавіатурною навігацією.

## 3. Відповіді на контрольні питання

### 1. Чому зовнішній CSS-файл кращий за inline styles для цього проєкту?
Зовнішній файл відокремлює структуру (HTML) від оформлення (CSS), дозволяє повторно використовувати єдиний набір класів і дизайн-токенів на всіх сторінках сайту (`index.html`, `login.html`, `register.html`, `create-mode.html`), зменшує обсяг повторюваного коду та кешується браузером після першого завантаження, що суттєво підвищує швидкість роботи.

### 2. Яку задачу вирішує `box-sizing: border-box`?
За стандартної блокової моделі (`content-box`) властивості `padding` та `border` додаються до заданих розмірів `width`/`height`, збільшуючи реальний розмір елемента і викликаючи небажане ламання сітки. Значення `border-box` включає внутрішні відступи та межі в загальну оголошену ширину і висоту елемента, роблячи розрахунки передбачуваними.

### 3. Які значення ви винесли в custom properties і чому?
У `:root` винесено палітру кольорів бренду Tetris (`--color-bg`, `--color-surface`, `--color-primary`, `--color-accent`, `--color-danger`), шкалу пропорційних відступів (`--space-1` – `--space-12`), радіуси заокруглень (`--radius-sm`, `--radius-md`, `--radius-lg`), параметри тіней та системний стек шрифтів. Це забезпечує централізовану модифікацію дизайн-системи, зменшує дублювання коду та виключає появу випадкових "магічних" значень.

### 4. Як каскад визначив переможне правило у знайденому конфлікті?
Каскад обчислює вагу селекторів за схемою специфічності (кількість ID, класів/псевдокласів, тегів). Якщо специфічність однакова, перемагає правило, розташоване нижче за текстом у таблиці стилів (порядок появи в джерелі).

### 5. Чому class selector зручний для компонента?
Селектор класу має збалансовану специфічність `(0, 1, 0)`. На відміну від селекторів за тегом, він не створює побічних ефектів для інших подібних елементів, а на відміну від селекторів за `#id`, його можна багаторазово використовувати для створення однотипних компонентів на сторінці (наприклад, декількох кнопок чи карток).

### 6. Як ви уникнули fixed height для довгого вмісту?
Для контейнерів і текстових карток не задавалася жорстка висота `height`. Натомість використано внутрішні відступи `padding`, природне розширення блоку контентом (normal flow) або `min-height` у випадках інтерактивних зон натискання (44px для полів і кнопок), завдяки чому довгий текст або збільшення масштабу браузера (zoom) не викликають переповнення чи обрізання.

### 7. Які form states реалізовано?
Реалізовано стан очікування (default), наведення курсору (`:hover`), активного натискання (`:active`), фокусування з клавіатури (`:focus-visible`), заблокований стан (`:disabled`) та стан валідації (`:invalid:not(:placeholder-shown)`), коли невірні дані підсвічуються червоною рамкою лише після початку введення.

### 8. Чому focus indicator не можна просто прибрати?
Індикатор фокусу є критично важливим елементом доступності (Accessibility). Користувачі, які керують комп'ютером за допомогою клавіатури (або скрінрідера), без індикатора не бачать поточний активний елемент, що робить інтерфейс непридатним для використання.

### 9. Де було доречне позиціонування, а де normal flow?
Основну розмітку сторінки (шапка, форма, ігрове поле, футер) побудовано за допомогою нормального потоку (normal flow) та гнучкого Flexbox для запобігання крихкості верстки. Абсолютне позиціонування (`position: absolute`) застосовано виключно локально для доступного посилання швидкого переходу (`.skip-link`), яке приховане за межами екрана і з'являється тільки при отриманні фокусу.

### 10. Які відмінності між Figma й браузером довелося свідомо адаптувати?
У Figma графічні елементи часто розміщуються з фіксованими координатами (`x`, `y`) та фіксованими габаритами. У браузері інтерфейс повинен адаптуватися до різної роздільної здатності екранів, зміни довжини тексту та масштабування. Тому фіксовані розміри замінено на гнучкі блоки з процентною чи `clamp()` розміткою, додано нативні інтерактивні стани взаємодії та забезпечено коректну ієрархію блокової моделі.
